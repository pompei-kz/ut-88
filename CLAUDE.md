# Правила работы с проектом

## Когда коммитить

**Коммитить можно только с разрешения пользователя или по его прямому указанию** («закоммить»,
«коммить по ходу работы» и т. п.). Без такого разрешения изменения остаются в рабочей копии,
а в ответе пользователю перечисляются и предлагаются коммиты (тип, short-comment, описание).
Разрешение действует на то, на что оно дано, и не распространяется на следующие задачи.

## Сообщения коммитов

Формат:

```
TYPE(short-comment) : Краткое описание задачи по-русски

Детальное описание.
```

- Первая строка начинается с префикса `TYPE(short-comment) :`, после него идёт краткое
  описание задачи на русском языке.
- Если в коммите несколько задач, их краткие описания соединяются плюсом `+`.
- После первой строки — два перевода строки (одна пустая строка), затем детальное
  описание.

### TYPE — тип изменения

| TYPE       | Когда использовать                                                                              |
|------------|-------------------------------------------------------------------------------------------------|
| `doc`      | документация                                                                                    |
| `feat`     | добавление новой функции                                                                        |
| `fix`      | исправление ошибок и недочётов в коде без добавления новой функции                              |
| `test`     | добавление и изменение автоматических тестов и кода, нужного только для тестов                  |
| `build`    | сборка и запуск проекта: Makefile, скрипты в `scripts/`, настройки сборки, `.gitignore`         |
| `plan`     | фиксация написанного плана                                                                      |
| `rules`    | внесение правил работы с проектом                                                               |
| `refactor` | реорганизация без изменения содержимого: перенос и переименование файлов, перестройка структуры |
| `prompt`   | фиксация задания (промпта) — файла с постановкой задачи                                         |
| `devi`     | фиксация файла отклонений от плана и самостоятельных решений (`NN-deviations-…md`)              |
| `todo`     | список задач и непроверенного (`todo.md`)                                                       |

### Ссылки на планы и задания

В коммитах типов `plan`, `prompt` и `devi` `short-comment` — имя файла без расширения, например
`prompt(01-prompt-create-emulator)`, а в детальном описании указывается полный путь к
файлу. В переписке и других документах на планы и задания тоже ссылаться по имени файла.

### Новый тип изменений

Если изменение не подходит ни под один тип из таблицы, **коммитить не нужно**. Вместо
этого:

1. описать, что это за изменение и почему оно не подходит под существующие типы;
2. предложить несколько вариантов нового типа (название и когда его использовать);
3. дождаться решения пользователя, внести выбранный тип в эту таблицу и только потом
   коммитить.

### short-comment

Очень краткий комментарий (латиницей, через дефис) по основной задаче коммита.
Например, написание эмулятора — `create-emulator`.

### Несколько типов изменений

Если во время работы сделано несколько задач разного типа, нужно сделать **отдельный
коммит для каждого типа**.

### Примеры

```
doc(magazine-to-md) : Перевод журнала ЮТ-88 в Markdown

Текст статьи разобран из DjVu, вычитан по изображениям страниц
и разложен по файлам doc/*.md; иллюстрации в doc/img/.
```

```
feat(create-emulator) : Эмулятор процессора КР580ВМ80А + загрузка ПЗУ монитора

Реализованы все 244 команды, загрузка monitor.bin по адресу 0000H.
```

## Оформление Markdown

Таблицы в файлах `.md` всегда выравниваются: ячейки каждого столбца дополняются
пробелами до одинаковой ширины, чтобы вертикальные черты `|` стояли друг под другом и
таблица читалась в исходном тексте. Строка-разделитель (`|----|`) тоже растягивается на
ширину столбца, с сохранением двоеточий выравнивания (`:--`, `:-:`, `--:`).

Пример:

```
| Адрес | Назначение           |
|-------|----------------------|
| 9000H | индикатор A          |
| A0H   | порт клавиатуры      |
| C000H | начало ОЗУ (1 Кбайт) |
```

Выравнивание делает скрипт `scripts/align-md.py ФАЙЛ.md` (для таблиц внутри блоков кода —
ключ `--code`) или `make align-md` для всех `.md` проекта.


## Задания, планы и отклонения

### Папки и имена файлов

Каждая задача лежит в своей папке `plans/NN-short-comment/`, например
`plans/01-create-emulator/`. Файлы в папке называются так:

```
NN-тип-short-comment.расширение
```

- `NN` — порядковый номер файла в папке, двумя цифрами: `01`, `02`, `03`… Каждый новый
  файл получает номер на 1 больше последнего в папке.
- `тип` — тип содержимого: `prompt`, `plan` или `deviations`.
- `short-comment` — очень короткое название задачи (латиницей, через дефис), например
  `create-emulator`.

| Тип          | Расширение | Что содержит                                  | Кто пишет                          |
|--------------|------------|-----------------------------------------------|------------------------------------|
| `prompt`     | `.txt`     | задание или дополнение к нему                 | пользователь (копируется как есть) |
| `plan`       | `.md`      | план выполнения задания                       | Claude                             |
| `deviations` | `.md`      | отклонения от плана и самостоятельные решения | Claude                             |

### Порядок работы

1. **Задание.** Пользователь кладёт задание в файл `01-prompt-short-comment.txt`
   (например, `01-prompt-create-emulator.txt`).
2. **План.** По заданию составляется план в следующем по номеру файле
   `NN-plan-short-comment.md` (например, `02-plan-create-emulator.md`).
3. **Дополнения к заданию.** Если, пока составляется план, пользователь пишет дополнения,
   каждое дополнение **копируется как есть, без правок**, в отдельный файл
   `NN-prompt-short-comment-to-prompt.txt` со следующим номером (например,
   `03-prompt-create-emulator-to-prompt.txt`), и план обновляется с учётом дополнения.
4. **Статус плана.** В самом начале файла плана указывается статус — одно из двух:
   - `**Статус:** не выполнен`;
   - `**Статус:** выполнен`.

   Новый план создаётся со статусом «не выполнен». Статус меняется на «выполнен», когда
   план исполнен полностью.
5. **Отклонения.** Во время исполнения плана ведётся файл
   `NN-deviations-short-comment.md` (например, `04-deviations-create-emulator.md`). В него
   записываются все отклонения от плана и все решения, принятые самостоятельно, без
   согласования с пользователем, — с указанием причины.
